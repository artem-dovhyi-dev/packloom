# How a packloom pack is laid out

```
<pack>/
  pack.json          name, version, minecraft, loader, loader_version, memory_mb
  mods.txt           one entry per line; Modrinth slugs, ftb:, url:, manual:; comments with #
  overrides/         copied verbatim into the instance: config/, defaultconfigs/, mods/ (non-Modrinth jars), options.txt
  <Name>-<ver>.mrpack  build output: modrinth.index.json (download links + hashes) + overrides/
  build-report.md/.json, smoke-test.log, smoke-report.json   generated, safe to delete
  server/            generated by pack-test; the loader server plus server/mods
```

Workflow: edit `mods.txt` → `/pack-build` → `/pack-test` → `/pack-triage` on failure → repeat.
The client (Prism Launcher) imports the mrpack; the server test runs the same jars headless, which catches
most load-time conflicts but not rendering or shader problems.

Facts that save time:
- The client is always `required`; singleplayer runs an integrated server. Only mark `client` for rendering/UI mods.
- Modrinth marks libraries as required dependencies most of the time; when a build fails with a missing
  dependency, the fix is one line in `mods.txt`.
- The mrpack format only allows downloads from Modrinth, GitHub and GitLab; everything else ships in `overrides/mods`.
- Forge 1.20.1 needs Java 17; 1.20.5+ needs Java 21. `pack-test` picks the right one.
- Prism keeps instances in `~/Library/Application Support/PrismLauncher/instances/<name>/minecraft/` on macOS.
